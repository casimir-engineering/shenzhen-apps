# Shenzhen Reader · Mobile

**Android first. iPhone next. A quiet reader, a reader-controls wheel, and a codebase that gives AI immediate evidence.**

Design specification · 24 September 2026 · Proposal, not an implemented application. Performance figures below are acceptance targets, not measured results. The browser prototype illustrates interaction and appearance; it does not contain production document engines.

## 1. The decision in one minute

Build a new **React Native + Expo + TypeScript** application. Share the interface and domain logic with a browser development surface. Keep PDF, EPUB, file-provider access and byte-intensive storage behind small native adapters. Do not port the macOS coordinator, custom window system or handwritten Markdown pagination engine.

The reader shows **one document at a time**. Groups live on a separate screen. A **reader-controls wheel** selects commands for the current document through one continuous Tools-down → slide → release gesture. It contains no document/group switching or library navigation. A standard controls list provides an accessible alternative. The corrected interaction and research are defined in [the reader controls UX study](control-wheel-study.md); previous document-switching wheel reviews are historical and do not validate it. Collection quietly retains local copies and revisions using shared immutable blocks, with visible storage accounting and conservative cleanup.

Ease of AI development is a release requirement: a small UI change must be reproducible in a named scenario, visible immediately, testable without compiling document engines, and accompanied by the appropriate browser and native evidence. This means architectural boundaries and tools, not an in-app chatbot.

| Decision | Recommendation | Why |
|---|---|---|
| Mobile shell | React Native, Expo development builds, TypeScript, Expo Router | Familiar component code and a shared browser feedback surface |
| Visual system | Material 3 conventions, a small token-based component set; standard controls first | Predictable accessibility and fewer custom widgets |
| PDF / EPUB | Thin native views around maintained engines; prove them before building the library | Reading fidelity and native gestures cannot be certified in a browser |
| Markdown | CommonMark + GFM rendered into a restricted local WebView | Reuse web layout and browser inspection; no new pagination engine |
| Persistence | SQLite runtime authority; versioned YAML settings/workspace import and export | Transactions and searchable metadata without competing live state files |
| History storage | Immutable content-addressed blocks; independent revision manifests | Exact recovery and reuse without fragile delta chains |
| Product boundary | Offline first; no account, cloud sync or document-upload AI required | Fast first use and a smaller development surface |

**Deliberate mobile differences:** no desktop tab strip, no permanent side panel, no separate Collection app, a proposed 1 GiB archive cap instead of desktop's unlimited default, and YAML as an interchange/debug format rather than a second live database. These are recommendations for this new application, not changes to the desktop app.

## 2. Reading comes first

Three entry points: Android **Open with**, **Share to Shenzhen Reader**, and the in-app system file picker. Cold launch resumes the last readable document; first launch presents Open a document and an unobtrusive sample. Never wait for Collection, thumbnails, a full-text index or every group's documents before painting the reader.

The reading screen has a compact title/source header and reserved bottom reader chrome with **Tools** and a standard **Controls list** alternative. Tools is the sole origin for the reader command wheel; down → slide through a family → slide into its command → release selects in one contact. The six families are Navigate, Zoom, View, Find, Notes and Document. The detailed study distinguishes direct commands from tools requiring text or other input. The page viewport ends above the control strip. A tap on unlinked whitespace can hide chrome; links, text selection, scrolling and double-tap zoom win gesture precedence. The labeled Tools origin remains reachable when secondary chrome hides; no preliminary reveal tap is required. TalkBack keeps navigation controls available rather than auto-hiding them. A header Organizer button opens the last organizer destination, with Groups and Collection as ordinary navigation choices and a clearly labeled Search action. Search there is global; Find in the reader searches only its document. No edge-swipe takeover of Android system Back. Back dismisses the topmost sheet/wheel first, then returns through screen navigation; it does not unpredictably switch document history. Organizer Back always returns to its invoking reader and position. On a cold organizer launch without a reader, Back follows the Android task stack. External opens create a reader return target rather than inserting an unrelated last-used document into that stack. Closing a sheet restores focus to its invoking control. Failed switches keep the previous readable document and announce the failure; recovery into a saved copy announces its dated identity.

PDF uses continuous vertical pages, pinch zoom, page entry, text selection and internal links. EPUB defaults to reflowed continuous reading, with font size, line spacing, theme and chapter navigation; reflow retains a semantic locator rather than a fabricated PDF page. Markdown defaults to reflow, supports headings, links, images, code and GFM tables, and keeps horizontal scrolling local to wide tables/code. Pagination/export fidelity with the desktop Markdown engine is not a v1 promise.

Positions are format-specific: PDF page plus normalized viewport; EPUB spine/resource plus locator/progression; Markdown block anchor plus text quote and local offset. Font, rotation and viewport changes re-anchor rather than restore raw pixel coordinates. EPUB progress says “Chapter 3 · 42%”; PDF says “12 of 48”. Older revisions retain their own position and never overwrite the live document's position.

### Source truth on a phone

Android documents are capability-bearing URIs, not dependable filesystem paths. Use the system Storage Access Framework and retain grants when the provider supports it. A provider may disappear or supply only a non-seekable stream. [Android document access](https://developer.android.com/training/data-storage/shared/documents-files).

| Source kind | Opening behavior | What the user sees |
|---|---|---|
| Persistable, available provider document | Open the provider's current original; snapshot asynchronously after first readable content | Original · provider name |
| Temporary shared URI / stream | Stage one private working copy while permission is valid; promote into Collection only after consent | Imported copy; Temporary copy if Collection is off |
| Retained revision, original unavailable | Resolve the verified recovery target below; read-only | Saved copy · Find original |
| Cloud provider still downloading | Cancellable provider/download progress; no false protection status | Downloading… with Retry/Cancel |
| Password-protected PDF | Prompt; optional remember using platform secure storage, keyed to content identity | Locked until authenticated |

Temporary shared files live in app-private `cache/reader-working`, under the same opaque native read lease used by rendering and capture; ArchiveIO must not stage a second whole file. With Collection off, close deletes the working copy once leases release. Backgrounding retains it for resume for up to 24 hours after last use; expiry only makes it eligible for deletion after all active leases release, never underneath a reader; process-death recovery keeps only the last active unexpired staged file if the OS has not purged it, and labels it Temporary. It is never guaranteed recovery. “Save locally…” exports through the system picker; if a temporary copy was lost, restore a placeholder with Reopen from source / Choose file, not a silently empty reader. Expiry and idle-cache cleanup run off the opening path. Unknown-length imports enforce the 512 MiB per-file staging limit and 512 MiB device reserve from the budget below, checking each block while streaming; cancel and delete the partial file if either is exceeded. Show progress and required/available space, not an unbounded import.

For stable capture, prefer a provider revision token or immutable descriptor. Check available identity/size/modification token before and after reading; retry twice if it changed. Without a provider guarantee, retain the exact captured byte stream, label it “Captured copy · source consistency unverified,” and do not call it a verified original revision. Rendering success or a hash alone cannot certify source consistency. A detected failed/torn read never becomes a visible revision. A complete but consistency-unverified stream may be durably Saved, but cannot replace the preferred verified recovery target. For app-managed staged files the lease prevents mutations, so exact capture is verified.

Each document stores two independent pointers: **newestCaptureID** is the newest complete, durable capture, including consistency-unverified captures; **preferredRecoveryRevisionID** is the newest complete capture verified coherent under a stable provider token/descriptor or immutable staged-file lease. “Saved” certifies storage integrity, not provider consistency. Selection follows this table, shared by Collection, History and resume:

| Available state | Default open / History entry point | Label and explicit alternatives |
|---|---|---|
| Original available; verified and newer unverified captures | Open current original | Live Original gets Latest; unverified saved row stays dated and labeled Unverified capture |
| Original missing; verified and newer unverified captures | Open preferredRecoveryRevisionID | Saved copy · date; that row gets Latest verified. Newer unverified row requires explicit selection and a consistency warning |
| Original missing; only unverified captures | Show recovery choice without auto-opening it | Open captured copy · date · consistency unverified, or Find original / Save a copy; no Latest badge |
| Failed, incomplete or detected torn stream | Keep previous pointers and readable document unchanged | Capture failed; Retry. No visible version for partial bytes |

History keeps saved captures in chronological order even when the preferred recovery row is older. When an available original is not byte-identical to a verified saved row, show a separate live **Original · Latest** entry; otherwise merge the live action into that matching row. Exactly one Latest or Latest verified badge exists, or none if only unverified captures exist. Explicitly opening an unverified capture always retains its dated warning. A later verified capture can advance both pointers. An unverified commit advances only newestCaptureID. This avoids silently choosing less trustworthy bytes just because they are newer.

A readable first page is not proof that the whole file has been archived. Source states and archive states are separate: **Original / Imported / Original unavailable** versus **Saving / Saved / Not saved / Paused**. Never show Saved until durable storage commits. For external edits, capture versions when reopening/resuming or receiving a supported provider notification; mobile background limits prevent a promise to capture every edit while the app is suspended.

If the original becomes unavailable, preserve the already readable view and use the recovery table for any reopen; offer **Find original** or **Save a copy** in a non-blocking sheet. Search only granted provider locations; no promise to scan the entire phone. Verify candidate bytes by hash, and auto-relink only a unique missing-source match. Identical content can share storage while retaining distinct document identities; names alone never merge histories.

## 3. Groups have their own place

The **Groups** screen contains named, colored groups and a search field that filters **group names only**. A group opens a dedicated document list. Browsing a group never changes the reading document. Tapping a document opens it at its saved position and makes that group active.

Create, rename, recolor, reorder, hide/show and delete groups. Each document has one home group in v1; moving changes membership, not content. Hiding removes a group from normal navigation, not storage or global search; Show hidden reveals it. Deleting a nonempty group offers Move documents to General, never Delete files. General behaves like any other group. Rename it and the next unassigned incoming document creates a new General. The explicit “Open into this group” action targets the browsed group; incoming external intents use General.

Group order, membership, visibility, scroll position, active group/document, reader-control layout preferences and reading positions survive process death. Document lists use thumbnails and a short position line. Overflow menus provide Rename, Move, History and Remove from group. Rename changes only the app display name. Move changes home-group membership; Remove from group moves it to General and is disabled in General. Close removes the document from the working set (and its group) but preserves original, Collection and reading position. Reopening a closed retained document puts it in General unless explicitly opened into another group. Archive-only documents need not be in any group until opened. A group is a working set, not the archive itself. The default General has a stable role independent of its label; renaming it clears that role, and the next unassigned open creates a new default. A manually named General is an ordinary group with a “Custom group” subtitle when disambiguation is needed. None of these operations delete original files or retained versions.

## 4. The reader-controls wheel

The wheel contains **current-document reader controls only**. Document/group switching remains in the organizer. This corrects the earlier specification's mistaken document-switcher interpretation. See [the complete UX study](control-wheel-study.md) and [primary-source comparison](control-wheel-comparables.md) for rationale, complete command routes, sequences and test gates.

A visible Tools control occupies reserved reader chrome above the platform's navigation area. A contact starting there displays the upward fan immediately, with no hold timer or initial tap. Slide through one of six fixed families—Navigate, Zoom, View, Find, Notes, Document—then continue into its expanded command fan and release. The same contact selects a command; family selection is not a separate tap. At most eight commands occupy the shared child fan; they are not crammed into the parent's narrow wedge.

The fixed center of Tools anchors the geometry; an off-center finger-down cannot move it toward an edge. In the 360-wide candidate, family lock is radius 90, inward branch correction 62, center cancel 24, and child band 108–160. Layout/capabilities/document identity freeze at down. No action happens on hover, and one valid release creates at most one command. Cancel, interruption, multi-touch or layout change creates none. Adjust zoom and Page scrub support outward continuation into a same-contact value rail, with preview then release-to-commit. Numeric/text entry and system share/print sheets are explicit alternative or additional tool inputs; do not claim opening their panel completes those tasks. Native pinch and page scrubbing remain standard alternatives.

Page-origin contacts stay with the reader even if they cross Tools. The wheel never installs a global long-press, double-tap, two-finger or edge-swipe shortcut. Android system/mandatory gesture insets and iOS safe-area/navigation constraints are respected without excluding or deferring system gestures. A standard controls list has equivalent accessible commands. Actual native arbitration, one-handed reach and the eight-child layout require the device/usability gates in the study; browser appearance does not certify them.

## 5. Collection: smaller by construction

On first document open, let reading begin, then ask once: **“Keep local copies and history of documents you open? Originals stay in place. Copies stay on this device.”** Choices: **Keep copies / Not now** (enable later in Collection → Settings); show the proposed 1 GiB limit and a Change link. Do not retain content before the answer, except temporary bytes strictly necessary to open a shared/non-seekable file. Turning Collection off stops new snapshots/indexing but preserves existing history. Import only documents the user has granted access to; do not crawl another app's recents.

Collection has one row per document, resolving the available original or the recovery target/choice defined in §2. No Latest badge on ordinary document rows. Search combines a thumbnail with highlighted text snippets. Selecting a match opens that exact document/location; History is a separate explicit action. Index only retained bytes after first paint, in cancellable batches, with clear “Text not indexed yet” states. Title search remains immediate. Each text hit carries document ID, exact content/revision identity, locator and index generation. Before navigation compare it with the live source identity. If unchanged, use the original; if changed or unverified, open the retained matching revision with “Match in saved version · date” and an explicit Open latest action. Never apply old offsets to new bytes. Open-document text search and in-reader Find use a separate cancellable in-memory engine search when Collection is off; closing removes it. Locked documents expose titles only until authenticated; no background password prompting.

Global search orders open document titles, group names, open-document text (first five), collected titles excluding already-open documents (first five), then collected text (first five). Results arriving asynchronously do not move the selected item. `col:` limits to Collection titles/text, including open documents. Show more expands that section. History versions do not flood the default results.

### Exact storage, not optimistic compression claims

**V1 format:** divide original bytes into fixed 1 MiB blocks; SHA-256 addresses unique immutable blocks. A small ordered manifest reconstructs each revision exactly. Identical files and unchanged blocks across revisions share physical bytes. Small documents are one block. Markdown asset files use the same object store and a revision dependency manifest; only granted local assets are retained. EPUB is retained as original ZIP bytes, not an unpack/repack approximation. Password-protected PDFs retain encrypted original bytes.

Whole-file hashing runs in the same background streaming pass as capture. No PDF byte array crosses the JavaScript boundary. Skip compression for v1 binary blocks: PDFs and EPUBs are often already compressed, and a codec is not allowed to delay reading. Small text/metadata can use the platform's standard deflate codec only when measured savings exceed overhead. No custom compression format or chained binary patches.

Fixed blocks intentionally favor simplicity, append-style PDF changes and fast restore. Insertions and ZIP rewrites can reduce reuse. A **content-defined chunking** upgrade is a separately measured option if the real corpus misses the storage target; version the chunker in each manifest so old revisions stay readable. Content-defined deduplication is an established approach, but its wins depend on the data. [Reference design: restic](https://restic.readthedocs.io/en/stable/100_references.html#backups-and-deduplication).

No permanent full-file duplicate alongside every chunked revision. Only leased active/incoming working files during handover and a bounded warm cache may duplicate retained bytes. Original-provider opens bypass reconstruction. A cold archived revision may need reconstruction into a seekable file: show a cached preview labeled Preparing saved copy, then enable interaction when ready. Large cold files cannot honestly have an unconditional instant-open guarantee. Even Android's platform PDF renderer requires seekable input. [PdfRenderer contract](https://developer.android.com/reference/android/graphics/pdf/PdfRenderer).

### Accounting and cleanup

Default archive cap: **1 GiB**, configurable to 256 MiB, 1 GiB or 5 GiB, custom or unlimited. Keep a 512 MiB device-space reserve; low space pauses new capture, never reading an already available original. The cap counts physical unique retained block bytes plus manifest/index overhead; the Storage screen separately reports disposable previews, working files and total app-owned bytes. Idle cache has a 128 MiB ceiling. Active/incoming staging and extraction follow the explicit handover budget below and are visible in accounting. Large imports that cannot be staged offer a precise space error and a provider/direct-open option when possible.

| Temporary storage category | Hard v1 bound / lifetime |
|---|---|
| Staged or reconstructed working files | One active A and at most one incoming B during handover; each ≤512 MiB, known or unknown length. A direct seekable original needs no staged file. Larger files can use direct access if the engine supports them; otherwise explain the staging limit |
| EPUB extracted resources | At most one set per active/incoming document; each ≤512 MiB inflated, including the per-entry limits in §6. These bytes count in temporary totals, separately from the original ZIP |
| Idle previews/working files/extraction combined | ≤128 MiB total; drop unleased extraction/working files first. The active exceptions end when their last lease releases |
| Block work buffers | ≤8 MiB; archive capture reuses the leased source, never creates another whole-file staging copy |
| Required remaining device space | ≥512 MiB after projected new allocations; checked before admission and per block, including permanent archive writes |

Peak additional temporary allowance is **working(A) + working(B) + extraction(A) + extraction(B) + 128 MiB idle + 8 MiB buffers**. Each working/extraction term is zero or at most 512 MiB; it is an upper bound, not eagerly allocated space. Retained archive and metadata are counted separately in total app-owned space. Preflight known file lengths and a conservative EPUB extraction allowance before admitting B; stream unknown lengths with the same bound and reserve checks. If preserving A plus B cannot fit, cancel B, remove its partial allocations, keep A readable and offer Free cache / Choose another file. Other apps can consume space after preflight, so runtime allocation failures follow the same rollback. Only after B emits interactive content does it replace A; release A and reduce unleased caches to the 128 MiB ceiling. A second incoming request cancels the first incoming generation; no third file is admitted. Expiry never deletes an actively leased file. Export can stream blocks without another materialized full file.

Cleanup first drops regenerable caches. Then rank documents by lowest user-open count, breaking ties by oldest last-open time. Remove each candidate's oldest unkept historical revisions before its latest copy; proceed to the next eligible document. Never automatically delete Kept revisions, active reader dependencies, pending exports, or the sole retained copy of an unavailable/import-only document. Also protect preferredRecoveryRevisionID while the original is unavailable or its availability/identity is unknown, even if a newer unverified capture exists: retaining that capture does not replace the verified recovery guarantee. Before evicting a latest copy, revalidate original availability with its granted capability and identity. Unknown, offline, revoked or unverified access is treated as unavailable: protect the last retained copy. Deleting a reference frees bytes only when no other revision owns the blocks. If protected data prevents meeting the limit, pause capture and offer Review storage / Increase limit. Never silently override Keep. Originals are never deleted. Explicit user deletion may remove a protected recovery revision only after naming that loss in the confirmation. Every revision deletion and pointer repair is one repository transaction: recompute newestCaptureID from remaining complete captures and preferredRecoveryRevisionID from remaining verified captures, or set either to null. Apply the §2 resolution table immediately; never leave a dangling pointer or promote an unverified capture to verified.

Storage shows **Used**, **Shared bytes saved**, **Temporary**, **Limit**, **Available on device**, and what cleanup would actually free. “Shared bytes saved” compares logical retained revision bytes with physical retained blocks; it is not a compression-ratio promise. Preview cleanup before applying a lower cap. Exclude a document, stop future collection, remove a history, and remove one revision are distinct commands with explicit scope.

### Crash-safe write protocol

The foreground TypeScript repository is the single SQLite writer and archive-mutation coordinator; no worker or native adapter writes SQLite. Its single serial command queue owns jobs and mutation order. ArchiveIO issues opaque process-scoped read/stage/GC lease handles and checks them on every byte operation; UI/domain code never handles paths or descriptor integers. Write and hash temporary blocks, flush/close them, atomically rename into the immutable object store, then commit the revision manifest/references, newestCaptureID and (only for a verified coherent capture) preferredRecoveryRevisionID in one SQLite transaction. Publish Saved only after that commit. Crash before metadata commit leaves reclaimable orphan blocks; it never exposes a half revision. GC takes a mutation lease, derives liveness from committed manifests plus active read/export leases, and deletes only unreferenced blocks. Use SQLite WAL with `synchronous=FULL`, enabled foreign keys and tested migrations. Native IO must fsync block data and affected parent directories before metadata publication; prove actual device behavior with power-loss/fault simulation, not just a rename test. Run bounded orphan recovery off the opening path. Verify reconstruction hashes before presenting/exporting a retained file. Fault-injection tests cover every phase, concurrent capture/delete, cancellation, full disk and missing/corrupt blocks. SQLite transactions do not themselves make external files atomic. [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html).

## 6. History and comparison

History is a reader sheet/full screen, not a second implementation inside Collection. Collection's History button opens the document using the §2 resolution table with History selected. Saved versions list newest first, with the live Original entry and **Latest / Latest verified** badge governed by that table; never award Latest to an unverified capture. Selecting an older revision opens it read-only and shows **Older version · date** in the reader header, with Return to latest (or Return to latest verified when the source is missing). Unverified captures keep their explicit warning. If linked, Latest always resolves the current original; its unchanged bytes need no new revision.

The Android launch scope includes version preview, Keep, Save a copy and missing-original recovery. Compare with Latest and Compare with Previous are the next delivery: on phones use a synchronized A/B toggle plus change list; on tablets/landscape, optional side-by-side panes. Added/removed text and images need labels and green/red marks plus navigation markers. Do not ship an unlabeled pixel difference as a semantic diff. EPUB comparisons use textual/structural locations and images, not unreliable page numbers. The domain contract and fixtures exist from v1; full visual comparison is explicitly outside the first Android acceptance gate.

### Supported format and resource profile

Initial target: Android 10/API 29 and newer, subject to the Gate 0 dependency/support audit. Test API 29, the pinned target API and the current stable OS. Declare target/min SDK from actual engine requirements rather than silently dropping older devices. PDF v1 includes ordinary/password-protected documents, text/link selection and image scans; unsupported encryption, XFA/dynamic forms and malformed documents get explicit errors, not a blank page. Scans remain readable without OCR.

| Format | Supported at launch | Graceful limitation |
|---|---|---|
| EPUB 2/3 | Reflow, contents, embedded fonts/images, links, fixed-layout through validated Readium capability | No DRM, publication scripting, multimedia overlays or editing; explain unsupported features |
| Markdown | CommonMark + GFM tables, strikethrough, task lists; local images with explicit grants | Raw HTML escaped; math/diagram fences remain labeled code; no desktop pagination parity |
| External resources | User-approved local folder/assets; external links open system browser | A file grant never implies sibling-folder access; missing assets show a placeholder and Grant folder action; remote assets off by default |

Bound EPUB extraction to 10,000 entries, 512 MiB total inflated bytes and 64 MiB per asset; reject traversal and symlink-like entries. Decode images into bounded tiles/thumbnails (maximum 32 million input pixels without a downsample path). Limit Markdown source for rich rendering to 10 MiB; larger text opens in an explicit plain-text mode. Exceeded budgets offer a readable unsupported/too-large explanation, never hang or silently omit content. The representative corpus validates and may refine these published limits before launch.

The WebView loads only an app-owned local origin and an allowlisted dependency map. Disable untrusted publication scripts, frames, file URL privileges and network loads. Only the app's injected navigation/selection bridge may execute; validate origin, frame, command schema, active document generation and payload size. Messages expose locator/selection commands, never arbitrary filesystem operations or eval. Password-protected documents use memory-only plaintext thumbnails/search while unlocked; no persistent plaintext index, screenshot cache or extracted preview. Locked status clears these derived buffers; retained bytes stay encrypted. Other private temporary files are excluded from cloud backup and cleared through the defined lifecycle.

Secure password storage uses Android Keystore-backed credentials and iOS Keychain later. Passwords never enter logs, YAML or preview fixtures. Collection/export retains encrypted source bytes. App-private storage is local recovery, not a backup against device loss or uninstall. Exclude archive/credential data from automatic cloud backup by default; make export deliberate. HTML scripts and automatic remote asset loads are disabled in EPUB/Markdown; user navigation to an external link goes through the system browser.

## 7. Architecture chosen for fast AI feedback

### Stack decision and alternatives

| Option | Strength | Cost for this brief | Decision |
|---|---|---|---|
| React Native + Expo + React Native Web | TypeScript, familiar React component model, shared browser scenarios, Android/iPhone path | Native document bridges still need native builds/tests; web layout is not identical | Recommended, subject to renderer spike |
| Kotlin + Jetpack Compose | Excellent Android integration and native previews/testing | iPhone strategy and browser feedback need additional UI work | Fallback if native adapters dominate effort |
| Flutter | Shared mobile UI and hot reload, strong widget/golden tests | Different Dart toolchain and browser evidence does not validate native plugins | Credible alternative; choose only if team/engine spike favors it |
| WebView-only/Capacitor reader | Straight browser iteration | Large-document gestures, file providers and engine accessibility are harder to make dependable | Not the default |

These are design judgments, not claims that native tools lack fast iteration. [Compose previews](https://developer.android.com/develop/ui/compose/tooling/previews) and [Flutter hot reload](https://docs.flutter.dev/tools/hot-reload) are established feedback tools. React Native's [Fast Refresh](https://reactnative.dev/docs/fast-refresh) supports rapid component feedback; [Expo development builds](https://docs.expo.dev/develop/development-builds/faq/) are necessary for custom native engines. Expo Go is not the production development plan.

Use Expo Router, React Native Gesture Handler/Reanimated for the wheel, one icon family, React Native Paper where its components fit, and React Native StyleSheet tokens rather than a custom design-system framework. Freeze compatible versions in the lockfile at the initial spike; this document does not invent future SDK version guarantees. Jest + React Native Testing Library exercise components and domain reducers; Playwright tests the browser scenario surface; Maestro plus native instrumentation tests Android flows. [Maestro](https://docs.maestro.dev/).

### Engines are adapters, not a new framework

PDF candidate: MuPDF's maintained Android engine through a small native view. EPUB candidate: Readium Kotlin navigator/publication APIs, Swift toolkit later. Markdown: markdown-it + a GFM table/strikethrough/task-list configuration, sanitized into a local WebView with a documented message bridge. Browser Markdown uses the same HTML/CSS; browser PDF/EPUB scenarios may use fixture surfaces clearly marked simulated. Do not imply those fixtures prove native text selection, rendering or DRM.

MuPDF reuse is conditional on a resolved distribution/license decision before adoption; an iPhone plan cannot ignore that gate. If the intended licensing/distribution is incompatible, choose a maintained commercially licensed PDF SDK or another validated engine at the spike, not after building the product around it. Readium provides Kotlin and Swift toolkits; it is not an official ready-made React Native bridge. [MuPDF licensing](https://mupdf.readthedocs.io/en/latest/license.html), [Readium Kotlin](https://github.com/readium/kotlin-toolkit), [Readium Swift](https://github.com/readium/swift-toolkit). DRM-protected EPUBs and unsupported encryption receive a clear unsupported message; DRM work is not in v1.

Create only three native boundaries: **SourceAccess**, **ReaderSurface**, **ArchiveIO**. Expo Modules supplies Kotlin/Swift module and view integration. [Expo Modules](https://docs.expo.dev/modules/overview/). Native code handles seekable descriptors, engine lifetime, file IO, hashing and block reconstruction. JS receives identities, metadata, locators and cancellable progress events; no base64 documents or per-scroll-pixel messages. Native reader gestures and wheel animations stay off a busy JS thread.

SQLite is the durable authority through **expo-sqlite, owned exclusively by the TypeScript repository**. Native ArchiveIO performs immutable byte operations, issues opaque leases and returns validated descriptors; it never changes manifests or SQL. Foreground/resumed jobs only in v1: TypeScript schedules bounded capture/index batches after first content. App backgrounding stops admission, persists a job checkpoint, requests native cancellation and commits only fully completed verified batches while the runtime is alive. No WorkManager/Headless-JS service is required. On resume, replay persisted jobs idempotently; no claim to capture while suspended.

Sequence: SourceAccess acquires the native source/staged-file lease → reader emits first interactive content → repository queues capture → ArchiveIO writes durable blocks under that lease → repository validates generation and commits references and the two conditional capture/recovery pointers in one transaction → UI receives Saved → release capture lease while the reader retains its own lease. A JS refresh cancels its generation and requests release; expiry/disconnect recovery cannot invalidate a still-active native reader lease. Process death invalidates all native handles; startup opens a new process epoch and uses committed references plus validated resumable staging records. Orphan files are recovered later, and GC cannot race a live write/read lease. Only complete source copies resume; partial streams are retried from their still-valid provider or discarded.

Pure domain reducers and policy decisions are shared across platforms and the scenario lab. A browser fake and the real Android repository must pass the same command/observable-state contract suite; Android alone additionally verifies SQL transactions, filesystem durability and descriptor lifetimes. UI never writes ad-hoc SQL. Expo SQLite's web support is currently alpha, so browser storage is explicitly a fixture implementation. [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/).

### Small contracts and a finite state model

| Contract | Required responsibilities |
|---|---|
| SourceAccess | Open/grant/revoke, capability flags, seekable lease or stage stream, detect identity change, locate/export |
| ReaderSurface | Open/cancel, first-content event, restore/get locator, find, selection, theme, close; explicit capability flags |
| ArchiveIO | Stream/hash/chunk, verify/reconstruct, stat physical bytes, atomic promote, bounded GC with leases |
| WorkspaceService | Group/membership commands, active document, positions, undo for reversible organization |
| CollectionService | Capture state, revision manifests, Keep/exclude/delete, quota preview, search index tasks |

All commands carry document/revision IDs and an intent/generation token. A cancelled or stale open/search/capture cannot overwrite a newer selection. Model reader states as idle → resolving → loading → readable, with password-needed/error/cancelled branches. Model capture independently as off → queued → saving → saved/paused/failed. No shared boolean can mean both “document available” and “backup complete”.

Database entities: Document, SourceReference, Revision, Block, RevisionBlock, Dependency, Group, Membership, ReadingPosition, Setting and Job. A document ID is distinct from source URI and content hash. Schema versions have forward migrations with rollback-safe backup/export; reject unsupported future imports without overwriting current state. YAML export/import includes versioned settings, groups, reader-control layout preferences and reading locators, validates schema and performs one transaction. It excludes credentials and archive payloads; cross-device source grants require reauthorization. No filesystem watcher racing the database.

Suggested boundaries: `app/` routes; `features/reader`, `groups`, `collection`, `history`; `domain/` pure types/commands; `data/` repository and migrations; `native/` three adapters; `ui/` tokens and primitives; `scenarios/` fixtures; `tests/` contract/native/performance. Features depend on public contracts, never reach into another feature's private state. Avoid a global coordinator, event-bus spaghetti and renderer-specific types in UI components.

## 8. AI development is a measurable workflow

Build the feedback tools before building all features. One command starts a browser scenario lab and a warm Android development build. Every screen and error state has a stable URL/scenario ID, a reset action, deterministic time/IDs/data and accessible element names. AI can navigate directly to `reader/locked`, `groups/long-names`, `collection/full`, `history/missing-source`, `wheel/all-controls` and `reader/stale-open` without manual setup. Production builds exclude scenario loaders and debug command bridges.

| Change | Smallest evidence loop | Required native follow-up |
|---|---|---|
| Spacing, copy, color, empty state | Hot refresh + browser screenshot/accessibility check | Native golden for changed screen before merge |
| Group/selection/history logic | Pure command tests + shared UI scenario | Process-death restore smoke on Android |
| Wheel behavior | Reducer tests + browser pointer/keyboard tests | Real touch, system Back, TalkBack, haptics, gesture cancellation |
| Engine / URI / archive | Native contract test against generated files | Emulator + a physical mid-range phone, fault/performance evidence |

Proposed local feedback budgets after a warm setup: component update ≤2 s; scenario screenshot ≤5 s; focused logic/component tests ≤10 s; focused native scenario ≤60 s excluding a cold native build. Repeat each of five ordinary changes 20 times after a warm setup (100 observations), report per-task p50/p95 plus all failures, record commands/environment, and investigate misses. A one-off run is labeled a smoke sample, not a percentile study. These are workflow gates, not promises that all native recompiles finish in one minute.

A feature task provides: outcome and non-goals; relevant contract; one small fixture; acceptance scenario IDs; allowed file area; exact commands; expected evidence. One implementing agent owns a module at a time; an independent critic reviews the result. Keep an architecture map and decision log concise. Compiler errors and test results return as structured JSON plus a screenshot/trace where relevant. Agents should not repeatedly rediscover the project or interpret a giant build log.

Definition of done: typecheck/lint, focused regression that covers behavior, relevant screenshot diff, applicable native smoke, state/low-space/accessibility checks, no background work on unaffected paths, and a short implementation note. Do not write dozens of source-text tests that merely assert code strings. Fail CI on unhandled errors, inaccessible primary controls, accidental network access in offline scenarios or stale-generation state overwrites. Do not grade a native reading feature from a browser mock alone.

Development-efficiency trial: implement five bounded UI/state changes after setup. Record wall-clock iteration time, failed build/test loops, changed files, and agent input/output tokens when available. Compare against the same five tasks in a frozen desktop baseline where feasible; report missing token data as unavailable. Pass if the warm UI loops meet the budgets, a typical task needs no coordinator/native edit, and failures are localized. Do not promise a made-up percentage reduction in token cost.

## 9. Performance, resilience and accessibility gates

Use release builds on a named physical mid-range Android phone (initial reference: Pixel 6a, 6 GB RAM) and one 4 GB low-memory device; record OS, thermal state, corpus hashes and cache condition. At least 30 runs per opening path. Measure two spans: **external cold start**, from the OS intent dispatch into a stopped app to the first displayed frame that accepts reading interaction (initial p95 target ≤1.5 s for the ordinary local corpus), and **source-ready open**, from a validated readable source lease to that same event (≤1 s). Record process start, JS ready, descriptor ready, first actual content frame and first accepted interaction in native traces. A cached preview or title is never the end event. Use force-stop between process-cold runs, close engine handles for renderer-cold runs, and label OS filesystem cache as uncontrolled/warm unless a documented device reset method is used. Separate picker/user-password/provider-network time and show it in end-to-end results rather than erasing it. Memory PSS includes the app plus attributable WebView renderer processes; disk accounting includes EPUB extraction, temporary and working files.

| Scenario / local corpus | Initial acceptance target |
|---|---|
| Warm switch between loaded documents | p95 interactive ≤150 ms |
| Cold local PDF ≤20 MiB / 200 pages; EPUB ≤10 MiB; Markdown ≤500 KiB | p95 first readable interactive content ≤1 s after valid source access |
| Large/scanned PDF ≤250 MiB or cloud/staged archive | Progress within 100 ms; cancellation ≤100 ms; report separate first-content/reconstruction metrics |
| Wheel highlight | p95 frame ≤16.7 ms on 60 Hz target; no repeated engine opens during hover |
| Name search, 10,000 documents / 500 groups | p95 initial results ≤100 ms; indexed text first results ≤300 ms |
| Collection capture enabled versus disabled | ≤10% regression in first-content p95; capture never precedes first content for available originals |
| Working memory, ordinary single document | ≤250 MiB peak process PSS target; bounded page/tile cache and pressure eviction |

Targets are subject to the early engine spike, but a failure must be documented and resolved or explicitly change the supported envelope before implementation scales. Test malformed files, large images/tables, CJK/RTL, accessibility text scale at 200%, reduced motion, one-handed use, keyboard navigation, lost URI grants, rotation, process death, interruption while staging, battery saver and offline providers. PDF image scans without OCR have no searchable text; say so rather than return misleading emptiness.

Storage benchmark is preregistered before selecting final storage format: at least 100 logical documents and 400 distinct revisions, including non-aligned incremental PDF saves (40% of source-byte weight), full PDF rewrites (25%), EPUB repacks (25%), and Markdown with small edits/shared assets (10%). Include 10 identical-but-distinct document identities and a separate unrelated/no-reuse set. Freeze fixture versions/hashes, tool/save procedures and byte weights so the corpus cannot be tuned to the implementation. Baseline is **whole-file content-addressed storage**, one full blob per unique revision hash, with the same catalog/index/preview policy; do not compare against duplicates that even simple deduplication avoids.

Pass when steady idle total app-owned bytes (retained payload, metadata, index and derived cache) are **≤80% of that baseline** on the mixed corpus, and the no-reuse set adds **≤5% or 8 MiB**, whichever allowance is larger. Report retained allocated bytes, steady idle total and peak total separately, after cache-policy stabilization. During capture/reconstruction and document handover, peak incremental temporary storage must obey the §5 formula, including both active/incoming working files and extraction sets, 128 MiB idle cache and 8 MiB block buffers. Report every term and enforce the 512 MiB remaining-device reserve; extraction cannot evade total accounting. If fixed blocks fail, benchmark a maintained CDC implementation with identical fixtures, first-content/CPU/battery/restore gates and bridge complexity. If neither meets the gate, change the design or explicitly narrow the space-saving claim before launch; CDC is not a guaranteed fix for recompressed containers.

Algorithmic checks remain separate: ten byte-identical opens add no new payload blocks; a 100 MiB PDF with five 1 MiB append-only revisions stays below 110 MiB retained payload plus metadata; repeated independent documents with identical content share bytes without merging identities. Measure rewrite-heavy PDF/EPUB files separately and publish the actual overhead. Restore/export must be byte-identical for every retained revision. A cap test must respect Keep/only-copy protection and never free a block still referenced by another document.

## 10. Delivery sequence and iPhone path

**Gate 0 — prove the risky seams.** Android development build plus browser scenario lab; local PDF/EPUB/Markdown, including at least one fixed-layout EPUB if that launch capability remains; real URI grant and non-seekable import; a wheel over the real reader surface; text selection/search; memory and first-content traces; ten exact round-trip archived files; engine licenses and distribution resolved. A small iOS simulator smoke must open the same three formats through the intended adapters before declaring the architecture portable. Do not invest in all library screens until this passes. If integration needs renderer internals or a large bridge framework, simplify or reconsider the stack.

**Gate 1 — Android daily reader.** Reader, Groups, accessible reader-controls wheel/list, position persistence, original/imported source labels, password handling, appearance and offline behavior. Validate process death and simultaneous incoming open intents.

**Gate 2 — Android Collection launch.** Consent, block deduplication, exact restore, searchable latest-document list, History preview/Keep/export/recovery, cap accounting/cleanup and fault-injection coverage. A “Collection launch” is not complete with duplicate full files and a speculative dedup roadmap. Fixed-block storage is the first measured implementation; escalate to CDC if its documented corpus fails the required target.

**Gate 3 — later Android enhancement.** Visual/semantic comparison, richer annotations/OCR, optional text-to-speech, advanced Markdown export. Each requires its own performance/accessibility contract. No sync, collaboration service or built-in cloud AI in these gates.

**iPhone product phase.** Reuse domain commands, schemas, screens, scenarios, tokens and reader-command wheel state machine. Implement SourceAccess with document picker/security-scoped resources and file coordination; Readium Swift for EPUB and the chosen licensed PDF engine; Keychain credentials. Validate safe areas, VoiceOver, Dynamic Type, app suspension, share extension/import lifetime and iOS navigation conventions. Do not carry Android Back behavior into iPhone unchanged. App Store compatibility and licenses must be settled at Gate 0; this is a later delivery, not an assumed free compile.

Named acceptance scenarios additionally include: `search/stale-original` (old match opens its exact dated revision); `import/opt-out-relaunch` (temporary availability/expiry is honest); `source/changes-during-capture` (exercise all four recovery-table rows and conditional pointer commits); `import/large-handover-reserve` (200 MiB temporary A stays readable when incoming 200 MiB B cannot fit the reserve); `cleanup/provider-disappears` (last copy and last verified recovery target protected, including verified V1 plus newer unverified U2); `history/delete-recovery-target` (explicit deletion atomically repairs pointers and enters the appropriate recovery choice); `archive/crash-before-commit`; `wheel/cancel-and-origin-ownership`; `reader/200-percent-text`; and `groups/close-reopen-general`. These join the earlier scenario lab and must execute against production contracts, not just static screens.

Definition of specification success: a developer can begin Gate 0 without inventing navigation or data ownership; major failure states have specified outcomes; mockups and state contracts agree. The earlier eight-round scores assessed the superseded document-switcher interpretation and are not evidence for this corrected control wheel. Its research, interaction evidence and unresolved device gates are recorded separately in the controls study.
