# ADR 0014: Sync between one person's devices

Status: Accepted (lead integrator, 2026-10-15). Date: 2026-10-14.
Plan: [friends-multi-device.md](../../../docs/plans/friends-multi-device.md) § Sync. Builds on ADR 0012 (the device
chain: who our devices are), ADR 0013 (joining: how a device becomes one), ADR 0003 (the store), ADR 0004 (presence
tags) and ADR 0009/0010 (online sessions). Areas: sync (`service/sync/`, interface `SZFriendsSync.h`), store (schema
v9, `service/store/SZFriendsStoreSync.h`), session (the SYNC frame), helper (`nearby/SZFriendsNearbyService+Sync.m`,
`+FriendDevices.m`).

## Context

The owner's words: "then all chats are synced p2p local first of course, online then"; "you can chat with yourself to
share files"; "erase chat history with confirmation for each chats or all" (deletions must reach every device). Devices
change things while apart (a laptop asleep, a desktop receiving), so sync must merge concurrent changes without a
coordinator and give every device the same store whatever order things arrive in.

## Decision

**Events.** Every change becomes an event signed by its device's key: `version | kind | author | seq | lamport | ms |
scope | subject | body length | BLAKE2b-256(body) | Ed25519 signature over root key || all of that`, domain
"SZFriends sync event v1". The body travels beside the header, so a deletion can drop it and the header still
verifies. Kinds: chain, profile, setting, person (one of four field groups), item (message, file row, history
event), read marker, outbox entry, file record, file held, tombstone. Bodies are tag-length-value fields with one
encoding each; times are the exact doubles the store holds, so every device stores identical times.

**Capture, not hooks.** The engine scans the store for what changed since it last looked: history rows with no
origin yet (oldest first, in batches), and for everything else the value it last recorded or applied (a register),
compared with what the store holds now. WHY: nothing a crash interrupts is lost to sync, the helper's many write paths
need no edits, and a profile with one device turns its whole history into events the first time another device
joins. Capture runs only while a session with another of our devices is live (launch is untouched).

**Merge rules**, each a function of the set of events seen, so every order gives the same store:
- items: an add-only set by (conversation, id); the same message reaching two devices keeps the earliest times;
- read markers: the maximum (received time, id); the unread count is recomputed from it. A device captures the item
  with exactly `unread` incoming items after it, which is what reading and later arrivals mean;
- person field groups (relation with automatic acceptance, profile, keys, trust), the profile and settings:
  last writer wins by (Lamport clock, author key). Keys only fill gaps: a stored key changes only through review;
- outbox entries: delivered wins, then last writer; file records: delivered or received wins, then last writer;
  who holds a file's bytes: the union, except that an author's FILE HELD saying it no longer holds them takes it out
  (amended by ADR 0016: each author's last FILE HELD decides);
- tombstones win: a deletion names the version vector its device had and removes every item one of whose events it
  covers, on every device, and the item stays deleted (a later copy, even a friend's redelivery, changes nothing).
  The bodies of the events that carried it are dropped and the file is compacted, as ADR 0003 deletes.

Events that need something not here yet (an item before its conversation) wait and apply when it arrives.

**People across devices.** A conversation is named in events by the person's root key (`k:`), or by the author's
conversation id while they have none (an Add by ID not answered yet), or `you`. Conversation ids are kept when free,
so a joined device mostly holds the same ids; when two devices met the same person apart, each keeps its own id and
events still meet on the key.

**Transport.** Our devices find each other nearby by tags from an own-devices secret and the device key (a secret
friends never hold; the first device draws it and sync carries it), advertised in one of the callback slots; online,
through the host's record of each device key, as the driver reaches a friend. They connect with IK to the static key
our chain gives the device, send CHAIN first, then SYNC frames (frame 26, field 35, up to 64,000 bytes, session minor
2). The exchange: HELLO with each side's version vector, then each author's missing events in order, at most four
EVENTS unacknowledged, ACK with the vector after applying, then anything new as it is captured or heard from a third
device. One session per device pair: when both dial, the one opened by the lower key stays.

**Friends reach any of our devices.** The first device keeps the person's presence tags; every other device advertises
tags from the person's presence secret and its device key, so a friend holding our chain knows which device it sees
and dials it with that device's static key; online the driver is asked for each device's record. A friend's message
is committed and acknowledged by whichever device it reaches and synced from there. Outbox entries for messages,
requests and presence secrets sync, so any device may deliver them (ids make duplicates harmless); file offers and
answers stay with the device that has the file or the receiver.

**Files.** File records sync at once (with who holds the bytes); history shows a file another device holds by its
name and size. Bytes up to 25 MB, and any file in You, copy by themselves; a larger one copies when asked (Get). A copy
runs over SYNC (WANT/PART/NONE), sixteen 48 KiB parts ahead, resumes from `received/.partial/`, and is published in
`received/` only when its whole digest matches the record.

**You.** A conversation with id `you` and no keys, made once the profile has a second computer; its items and files
sync like any other and never go through the outbox. A message there is "On all your computers" once every other
authorized computer said (its last HELLO or ACK, kept per device) it holds an event that carried it; a file once
every other computer holds its bytes.

**What a removed computer still counts for** (amended on acceptance). The device that revokes another records which of
its events it held (event kind 11, the revocation's coverage); our devices take a revoked device's events up to there
and none after, whoever forwards them, and only a record from the device that signed that revocation counts. A device
that took some of the later ones before the record reached it drops them when it applies the record (amended after
review): they leave the log, the items only they brought go as erased history goes (free pages wiped, though not marked
deleted, so an honest copy from a friend may come again), and every value one of them was the last to write (a name, a
person's fields, a read marker, an outbox or file state) is worked out again from the events left, by the same rules;
with none left, it goes back to never written, as on a device the late events never reached (no own name, no read
marker), and what a device still shows otherwise it sends as its own change (see Consequences for settings and a
person's fields). A change made on that device and not yet recorded (a name typed over the removed computer's) is
recorded as its own first, so it stays and nothing is worked out again over it. So every device ends with the same store
whichever order the late events and the record reached it. A void device (added only by links a revocation voided, ADR
0012) never spoke for us: its events are left out of a batch, which still counts, and never offered on.
An event whose Lamport clock is more than 2^32 ahead of ours is refused, so no device runs the clocks to their end. A
tombstone takes only events older than itself by clock: what its device could have seen, never later messages. The
Friends ID never travels by sync (it is the person's on the host, whose welcome gives each device the ID it holds).
After a revocation the first authorized computer draws new presence and own-devices secrets, which sync carries to the
others, and queues the new presence secret for every friend, so the removed computer matches nothing any more. Should it
not have done so 10 minutes (`SZFriendsSyncSecretRenewalWait`) after another computer first saw the removal (it is
away), the second authorized computer in the order every device computes alike draws instead, then the third after 20
minutes, and so on; the setting `renewed` (a digest of the removed devices) syncs with the secrets, so a computer coming
back after another drew takes those rather than drawing its own. Should it hear of the removal before those secrets
reach it and draw as well, one draw wins on every device by the usual rule, and the computer whose draw lost tells
friends the winner too, so none keeps a secret that matches nothing. When a computer first saw the removal is kept, so a
helper that restarts while its computer waits its turn looks again shortly after start (never on the way to the first
snapshot), not only at the next change to the profile's computers. Each device keeps the last 4 own-devices secrets it
replaced, by which our devices still find a computer removed while away and tell it (ADR 0012).

## Alternatives considered

- **Hooking every write path** to emit events: lost events after a crash between the write and the event, and dozens
  of edits across the helper. Capture by comparison costs a scan per capture, bounded by batching.
- **Lamport-ordered tombstones** ("delete everything older"): a device that had not synced for a while would delete
  messages the person never saw. Version vectors delete exactly what the deleting device had.
- **A whole person record as one register**: two devices changing different fields at once would lose one change.
- **Sending the whole store on join**: no merge with what the new device then does apart; events are the bootstrap.

## Consequences

- The log keeps every event (bodies of deleted history excepted): roughly the history's size again. Compaction into a
  snapshot event is future work.
- A device whose chain revoked it stops syncing at once (its sessions close); events it signed before stay valid.
- A friend whose helper predates the chain only reaches our first device; our other devices still deliver to them.
- Our own-device tag takes one of the four callback slots, so with four Add by ID requests pending one waits.
- Profile edits made on a just-joined device before it heard the profile's events may lose to older ones by clock.
- Events a revoked device signed after the revoking device last heard from it are lost, even when honest: revoke a
  computer after it synced, when possible.
- A deletion the removed computer made after its removal, if it reached one of our devices before the record, stays
  applied there: the bodies it dropped are gone. The record still keeps it from every device it had not reached.
- When the late events were the only ones to write a setting or a group of a person's fields, only the profile and
  read markers go back to empty. The store keeps no "never written" for a setting (a secret) or a person's fields (a
  friend's relation, keys or trust), so the register goes back to never written while the store keeps the removed
  computer's value, and the device that heard it sends that value as its own change: every device ends alike, with
  what the removed computer wrote. The secrets drawn after the removal replace its settings; a friend's fields it
  alone wrote stay until the person changes them on one of their computers.
- Not done here: an end-to-end run of two and three helpers in the e2e harness (the e2e area).
